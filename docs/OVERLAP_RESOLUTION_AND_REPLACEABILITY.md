## 第一部分: 重叠功能解决方案

### 1.1 VFS vs DSTU — 互补架构 ✅ 无重叠

**验证方法**: 分析全部 `vfs_*` 和 `dstu_*` Tauri 命令注册，逐对比较处理器实现，追踪前端调用路径。

**分层架构**:

```
┌─────────────────────────────────────────────┐
│  前端                                        │
│  ├─ 学习中心 → dstu_* (CRUD/文件夹/回收站)    │
│  ├─ 文件上传 → vfs_* (OCR/索引管道)          │
│  ├─ Todo/Pomodoro → vfs_todo_* / vfs_pomodoro_* │
│  └─ RAG/搜索 → vfs_search / vfs_rag_*        │
├─────────────────────────────────────────────┤
│  DSTU 访达协议层 (无独立存储，全部委托给 VFS)   │
│  - dstu_create / dstu_get / dstu_update / del │
│  - dstu_list / dstu_search / dstu_export      │
│  - 文件夹管理 / 路径路由 / 回收站 / Watch 事件  │
├─────────────────────────────────────────────┤
│  VFS 虚拟文件系统 (内部服务层)                 │
│  - 仓库: VfsNoteRepo/FileRepo/MindMapRepo/... │
│  - 专门服务: OCR/PDF处理/索引/RAG/Todo/Pomodoro │
└─────────────────────────────────────────────┘
```

**关键证据**: DSTU 处理器内部始终 `use crate::vfs::repos::Vfs*Repo`。DSTU 没有自己的表、索引或存储。

**前端调用分布**:
- `dstu_*`: 学习中心浏览、资源 CRUD、文件夹、回收站、导出
- `vfs_*`: 文件上传(含 OCR 管道)、Todo/Pomodoro、OCR/PDF处理、索引、RAG

**行动**: 在 `dstu/mod.rs` 和 `vfs/mod.rs` 顶部添加分层架构文档注释。无需删除代码。

### 1.4 Memory vs VFS — 领域服务层 ✅ 无重叠

**验证方法**: 分析 `MemoryStorage` trait 实现，追踪 `VfsMemoryStorage` 的每个方法调用。

**关键发现**:
- Memory 笔记**就是** VFS 笔记 (`resource_type = "note"`)
- Memory 文件夹**就是** VFS 文件夹
- Memory 搜索**就是** VFS LanceDB 混合搜索
- `VfsMemoryStorage` 是薄包装器，所有操作委托给 VFS

Memory 添加的是**语义层**: LLM 驱动的记忆决策 (ADD/UPDATE/APPEND/DELETE)、时间衰减、记忆类型/目的、自动提取、进化。VFS 中没有 `VfsResourceType::Memory` — 因为不需要，Memory 笔记存储为 `Note` 类型。

**结论**: 无需变更。当前领域服务在 VFS 之上的分层是正确的软件架构。

### 1.5 file_manager vs unified_file_manager ✅ 无重叠

**验证方法**: 比较两个模块的完整公共 API，追踪所有导入和使用点。

**核心差异**:

| 能力 | `FileManager` (struct) | `unified_file_manager` (free fns) |
|------|----------------------|----------------------------------|
| 图片压缩/Base64/保存 | ✅ 专门 | ❌ |
| 存储空间计算 | ✅ | ❌ |
| 笔记资源管理 | ✅ | ❌ |
| Android content:// URI | ❌ | ✅ |
| SHA-256 流式哈希 | ❌ | ✅ |
| Magic-byte 检测 | ❌ | ✅ |

`unified_file_manager` 的 "unified" = 统一处理本地路径 + 移动端虚拟 URI。`FileManager` = 有状态的应用数据管理服务。

**使用方**:
- `FileManager`: 10 个文件 (lib.rs, commands.rs, exam_sheet, pdf_ocr, 等)
- `unified_file_manager`: 13 个文件 (commands.rs, data_governance, vfs/repos, chat_v2/tools)

**结论**: 无需变更。两个模块服务不同目的，没有任何函数重复。

## 第二部分: 学习组件可替代性评估

### 2.1 作文批改 — 建议保留 UI，精简后端

| 维度 | 评估 |
|------|------|
| 总代码量 | ~8,458 行 |
| LLM 依赖度 | **高** — 核心管道 ~200 行 Rust 仅是提示词组装 + LLM 调用 + 正则可解析 |
| UI 特殊性 | **极高** — 流式 XML 增量解析器 + 6 种内联标注渲染 |

**核心发现**: 后端是薄 LLM 包装器，但前端是高度定制化的。关键组件:
- `streamingMarkerParser.ts` (497 行) — 处理 SSE 块边界的部分 XML 标签
- 6 种 XML 标注类型的视觉渲染 (`<del>` 红色删除线、`<ins>` 绿色下划线 等)
- 4 Tab 结果视图 (标注正文/逐句润色/范文/评分卡)

**Skill 化可行性**: ❌ 不能。SKILL.md 无法定义自定义流式 XML 解析器或内联标注 UI。

**简化方案**:
1. ✅ 将 10 个内置评分模式提取为外部 JSON/YAML 文件 (消除 ~600 行硬编码)
2. ✅ 将核心管道提取为共享 LLM 工具
3. ✅ 保留前端标注渲染组件 (不可替代的核心价值)
4. ✅ 将会话 CRUD 整合到 DSTU 协议

**结论**: **保留独立模块，精简后端**。前端标注渲染是核心价值，不可替代。

### 2.2 翻译工作台 — 建议保留前端，后端可选 API 替换

| 维度 | 评估 |
|------|------|
| 总代码量 | ~4,965 行 |
| LLM 依赖度 | **高** — 整个后端是"发送文本 + 领域预设 → LLM → 流式翻译" |
| UI 特殊性 | **高** — 双语对照视图 + 同步滚动 + 自适应布局 |

**核心发现**: 后端 (~1,210 行) 大部分可替换。前端 (~3,755 行) 有大量不可替代的自定义 UI:
- 双语段落对照 (`ComparisonView.tsx`)
- 源码和目标面板同步滚动
- 自定翻译 (带智能防抖)
- 内联编辑 + Markdown 导出
- 移动端自适应布局 (水平/垂直/堆叠+触控滑动)
- DSTU/VFS 持久化

**API 替换可行性**: ✅ DeepL API 或 Google Translate API 可以替换 LLM 后端:
- 翻译质量更高 (专用引擎)
- 更便宜 (按字符而非 Token)
- 更快 (同步 API，无需流式管道)
- DeepL 支持术语表和正式度

**但会失去**:
- 聊天内联翻译弹窗的对齐 NDJSON 模式 (LLM 特有功能)
- 用户自定义提示词 (DeepL 不支持)
- 创造性/文学性翻译的灵活性

**结论**: **保留前端工作台**。后端可以添加 DeepL/Google Translate 作为可选引擎，与 LLM 并列。

### 2.3 思维导图 — 不可替代，建议保留全部

| 维度 | 评估 |
|------|------|

| UI 特殊性 | **极高** — 6 种布局引擎 + 5 种连线类型 + 3 种节点类型 |

**核心发现**: 这不是 LLM 包装器。这是完整的交互式思维导图编辑器:
- **6 种自定义布局引擎**: tree/balanced/logic-tree/logic-balanced/orgchart-vertical/orgchart-horizontal
- **ReactFlow 深度集成**: 5 种自定义连线类型 (curved/straight/orthogonal/step/orgchart) + 3 种节点类型
- **节点 CRUD**: 递归增删移动缩进/伸出，含父→子验证、深度限制(100)、节点数限制(10,000)

**Mermaid/Markmap 替换可行性**: ❌ 仅能替代**只读渲染**。不能替代交互式编辑 (拖拽、添加/删除节点、内联编辑、右键菜单、键盘快捷键、撤销/重做、遮罩背诵)。

**结论**: **保留全部**。自定义交互基础设施的投资巨大，与应用的 VFS 存储深度集成。

### 2.4 练习/考试 — 不可替代，建议保留全部

| 维度 | 评估 |
|------|------|
| 总代码量 | ~20,000+ 行 (Rust 16,837 + TS 4,000+) |
| LLM 依赖度 | **~30%** — 题目导入/生成的 VLM+LLM 管道；70% 是自定业务逻辑 |

- **同步/冲突解决**: 跨设备题目数据

**Anki 替代可行性**: ❌ 仅 SM-2 算法部分 (~500 行) 可被 Anki 替代。但题目导入管道 (VLM + 跨页合并 + 图片提取) 是核心价值。

**结论**: **保留全部**。子系统庞大但内聚。题目导入管道是核心差异化功能。

### 2.5 Pomodoro 计时器 — 建议移除 🗑️

|------|------|

### 2.6 Todo 任务管理 — 建议替换为外部集成

| 维度 | 评估 |
|------|------|
| 总代码量 | ~5,581 行 (前端 1,996 + 后端 3,585) |
| 核心逻辑复杂度 | **中** — 优先级/截止日期/标签/子任务/重复规则 |
| 成熟替代品 | Todoist API, TickTick API, Microsoft To Do |

**核心发现**: 功能中等但缺乏高级特性 (自然语言输入、协作、GTD 上下文、看板、日历集成)。

**替代方案**: Todoist 或 TickTick 的 API 提供相同甚至更强的功能:
- 自然语言日期解析 ("明天下午3点")
- 协作/共享列表
- 跨设备同步
- 日历集成

**但需要权衡**:
- 失去本地优先存储 (VFS 本地 SQLite)
- 失去 Pomodoro 集成 (但 Pomodoro 建议移除)
- 聊天集成 (LLM 可列出/搜索/创建 Todo) 可通过 API 包装器保留

**结论**: 🗑️ **替换为 Todoist/TickTick API 集成**。保留聊天工具接口 (LLM 可操作 Todo)，但将存储和 UI 委托给外部成熟应用。
